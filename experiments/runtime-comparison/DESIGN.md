# Experiment: Kajo against other runtimes, and the performance report

Status: briefed 2026-11-07 (the owner: real benchmarks against the big
runtimes, the report as markdown in the repository with SVG graphs,
re-runnable with a `just` command). Evidence, not production code, except
`scripts/perf-report.py` and the recipes.

## What this answers

How fast Kajo's interpreter and collector are against the runtimes a
reader knows, on the same machine on the same day, in numbers a reader can
reproduce; and a report the repository carries that says so with graphs,
regenerated from raw files whenever the experiment runs again.

Two deliverables, both re-runnable from one `just` recipe:

1. The comparison experiment (`experiments/runtime-comparison/`:
   `DESIGN.md`, this text; `programs/<kernel>/<runtime>.*`; `bench.sh`
   writing `bench-raw.txt`, one line per run with runtime, version,
   kernel, workers, ms, checksum and thermal state), run twice: once on
   the commit before the interpreter-speed module as the baseline, once
   on its result.
2. **The performance report in the repository**, `docs/performance/README.md`
   with its graphs as SVG files beside it (`docs/performance/*.svg`),
   generated by `scripts/perf-report.py` (Python 3 standard library
   only, hand-written SVG as `shell-report.py` makes its tables) from
   the raw files: the comparison's `bench-raw.txt`, Kajo's own kernel
   A/B lines (`just bench`'s raw output, cycles and instructions per
   kernel from the per-thread counters once the interpreter module adds
   them), and, when the paths are given, the latest device matrix rows
   (`scripts/shell-report.py`'s inputs) for the collector section. The
   README is one file: hand-written prose, and generated blocks between
   `<!-- generated: <name> -->` and `<!-- /generated -->` markers that
   the script replaces in place, so the prose is edited by hand and the
   numbers never are. `just perf` runs the comparison and Kajo's
   kernels and regenerates the report; `just perf-report` regenerates
   from the raw files alone. The report's date, commit and machine come
   from the raw files' header lines.

   The hand-written part 0, written by the main session, not the agent,
   describes what kind of VM and collector Kajo is and what each choice
   buys and costs; the agent leaves the markers for it. The generated
   parts: the throughput table and graph per kernel and runtime
   (horizontal bars, log scale where runtimes span decades, Kajo's bars
   filled and the others outlined, one SVG per graph with its own
   `<title>` and the values as text beside the bars so the SVG reads
   without color), Kajo's 1-against-8-worker scaling, the Smalltalk
   library kernels against Pharo, the collector pauses where reported,
   the device rows when given, and a caveats block the script fills
   from the raw data (which runtimes were missing, thermal states seen,
   checksum refusals). Every SVG uses `currentColor` for text and axes
   and a small fixed palette for the series, so it reads on GitHub in
   both themes; no external fonts.

Evidence, not production code, except the script and the recipe, which
are tested the way `shell-report.py` is: a fixture raw file and a
golden README section in `Tests/KajoCompilerTests/Fixtures/`.

## Runtimes

Installed on the mini with Homebrew unless noted, versions recorded in
`RESULTS.md`: Kajo (the aligned `-enable-testing` release build, kernels
in kasm and in Smalltalk), Pharo 12 with Cog (the zeroconf download,
`curl get.pharo.org/...`, into the experiment's directory, never into
the system), CPython 3 (the newest Homebrew one), Lua 5.4, LuaJIT (with
the JIT and with `-joff`, the best hand-written interpreter there is),
Node (with the JIT and with `--jitless`, V8's Ignition interpreter),
Ruby (with and without `--yjit`), a JDK if `brew install openjdk` is
quick (G1 and ZGC for binary-trees' pauses with `-Xlog:gc`), and C at
`clang -O2` as the floor. Record `ProcessInfo.thermalState` (the shells'
helper or `pmset -g therm`) at each run's start; repeat the first kernel
at the end.

## Programs

The same algorithm, written idiomatically in each language with no
library help beyond arrays and dictionaries, parameters chosen so the
fastest runtime takes about a second and the slowest under a minute:

1. `fib`: recursive Fibonacci, calls per second. Kajo's `fib` kernel is
   this.
2. `dispatch`: one polymorphic call site over three classes plus an
   indexed read per iteration, as Kajo's `sends` kernel.
3. `binarytrees`: the Benchmarks Game program at depth 16 with a
   long-lived depth-12 tree, as Kajo's `alloc` kernel; allocation and
   collection throughput. For the collectors that report them (Kajo's
   counters, Pharo's `Smalltalk vm` statistics, the JVM's log), the
   pause p50, p99 and max beside it.
4. `collections`: Smalltalk against Pharo only, the library kernels the
   kernel-image bar never had: fill an OrderedCollection of a million
   SmallIntegers and sum it with `do:` and `inject:into:`; a Dictionary
   of 200 000 Symbol keys built and looked up; a String of a million
   characters built with a WriteStream and scanned; sorting 500 000
   SmallIntegers. In Pharo the same methods; in Kajo the kernel's.
5. `arith`: the special-bytecode loop (`sum of (i * 3 + 7) mod p`), as
   Kajo's `arith` kernel, for the bytecodes-per-second line.

Every program prints one checksum; the harness refuses a run whose
checksum differs from the others' for the same kernel. Five runs
interleaved by runtime, medians with min and max, one thread for all;
Kajo additionally at 8 workers for `fib`, `dispatch` and `binarytrees`
(the one aggregate row, labelled as such).

## What the report's generated parts and the experiment's notes say

The tables; calls, bytecodes, objects per second derived from the
counts; a paragraph per kernel (hand-written in `DESIGN.md`'s results
section, not generated) on what the gap is made of (a JIT, a register
bytecode, an inline cache, allocation inline, a library) with the
evidence; what could not be made comparable and why; the thermal log.
No conclusion about Kajo's design that the numbers do not carry. A
runtime that does not build or run on this Mac is left out of the
report without a mention; the experiment's notes may say it was tried.

## Rules

No gate or agent runs on the mini while this measures. Nothing is
installed outside Homebrew and the experiment's directory; no system
setting, keychain or network change. The devices are not used. Kill
every process before hand-back; the harness bounds every run with
`gtimeout`.
