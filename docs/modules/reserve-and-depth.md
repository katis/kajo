Status: brief, written 2026-11-04 from two findings (module 9a's open

## 1. The stop-the-world scavenge's promotion reserve

`docs/modules/nursery.md` (module 4) says: "Promotion that still finds no
block traps with a counted report (`reserveExhaustions`): a provisioning
failure, never hidden." The trap is `preconditionFailure` in
`Sources/KajoVM/Nursery/Scavenge.swift` (`bumpPromotion` answering nil).
Module 9a's ring scenario (`apps/Shared/smalltalk`, ShellBench; the
scenario matrix `scripts/shell-matrix.sh`) hits it in every run under the
stop-the-world oracle mode at the default 600 MiB heap, while the local and
offloaded modes with concurrent marking never come near it. A crash of the
oracle every other mode is checked against is not a provisioning failure of
the owner's; it is the oracle running out where its design did not expect
to.

Build: when promotion finds no block, the scavenge **does not trap**. It
counts the exhaustion (`reserveExhaustions`, as now), reports it in the
run report and the shells' telemetry, and recovers inside the rules module
4 and the later collectors set: decide whether the right recovery is to
grow the reserve from the free blocks the soft limit still allows, to
finish the scavenge by keeping the remaining survivors in place (a
nursery that is not emptied this round, treated as module 7's keeps are),
or to end the scavenge and request a full collection that promotes the
rest; read nursery.md, young-collection.md (module 7's own fallback when
its budget runs out) and the models under `docs/models/` first and choose
the one that needs no new cross-thread protocol, or model it if it does.
The soft limit's accounting (`fullRequested`, the next poll's full
collection) stays as module 4 defines it. Then explain in the doc **why**
the oracle exhausts a reserve sized at twice the nurseries on the ring:
the ring promotes almost everything it survives (65 536 nodes replaced
every 1.3 million iterations) and the full collection that would free old
space never runs inside a scavenge; say whether the reserve's sizing rule
or the fallback was wrong.

Tests: the ring scenario at 600 MiB under the oracle runs to its end in
the macOS shell (`just mac-shell`, three runs, the count of exhaustions
reported, 0 frames counted as missed because of a trap); a `KajoVMTests`
test drives a kasm or Smalltalk load that exhausts the reserve on a small
heap under every collector mode and checks the counter, the report and
that the random-program oracle still agrees with its model (`just soak`
with the small-heap configuration added to its matrix if the soak does
not reach exhaustion today; say whether it does). The `just golden`
checksums are unchanged.

## 2. The parser's depth against a thread stack

Module 8d bounded unary and binary message chains to the parser's nesting
limit, 256, after a chain of thousands overflowed the Swift stack in code
generation (ASan under `just fuzz syntax`). 8d's open question 4: a debug
build's code generation still overflows a 512 KB thread stack (a Swift
Testing or worker thread) at about 100 levels; the fuzzer runs on the main
thread's 8 MB and never sees it. The bootstrap compiler runs in `kajo
build-image` and in tests; the Smalltalk compiler runs on the interpreter
with its own stack and is not affected, but the limit is shared and the
comparison test must hold.

Build: measure the stack a debug and a release build of the bootstrap
compiler use per level of nesting (brackets, blocks, chains, cascades,
keyword messages with nested arguments), on a 512 KB thread, and either
make code generation and the parser's recursion for chains iterative (a
chain is a left-deep tree; it can be generated by a loop), or lower the
nesting limit to what fits the smallest stack the compiler runs on with a
margin of 4, in both compilers and in ADR 0009's "Built" notes. Prefer the
iterative chain, since it removes the pressure rather than the symptom,
and keep the limit for brackets and blocks where recursion is the natural
shape. A test compiles, on a thread of 512 KB (`Thread` with
`stackSize`), the deepest input every construct allows at the limit, in
debug and release, and a syntax fuzz run (`just fuzz syntax 600`) runs on
such a thread as well (add the option to `fuzz-syntax`'s driver, or run
the fuzzer with `-rss_limit_mb` and a `pthread` of that size; say what was
done).
