## What it hides

- How a native application gives the VM its main thread: turns on a
  wakeup, after a native event and at every display refresh, with the
  frame account the experiments used (4 ms of each frame for the VM, then
  UI-priority turns of 0.5 ms only), and how the stuck report reaches the
  shell.
- How a native event reaches a Smalltalk handler (a queue the shell fills
  from any thread, a Semaphore, one Process on the main thread) and how a
  view call reaches the native view (one hop primitive, a handle table in
  the shell). The same Smalltalk protocol drives AppKit and UIKit; the
  platform is behind the primitive (ADR 0010).
- How Swift code holds Smalltalk state across turns: it does not hold
  oops. A Process the shell spawned is a `ShellProcess` handle the VM
  roots until the shell releases it; every other value crosses by copy as
  a `ShellValue`.
- How the two Xcode apps are put together: the Swift they share
  (`KajoShellCore`, a package target), the images a build phase makes with
  the PATH toolchain, the launch arguments, the output files, the device
  script.

**Threads.** `runTurn` and `checkStuck` run on the shell's main thread: the
main worker (worker 0) is that thread for the length of the call. Every
other call may come from any thread and enters the VM on the host worker
as a primitive does (module 3's rule: host code reads no heap object
outside the VM). The callbacks are Swift closures the bridge calls through
module 3's C hooks (`VMHooks.context` and the new `VMHooks.host` point at
the bridge, unretained; `ShellVM` keeps it alive): `wakeMain` from any
thread, `views` on the main thread inside a turn (in a blocking region, so
young-collection rounds and stops are acknowledged by proxy while the
native toolkit works), `release` from the finalization Process's worker,
`events` from the emitting VM thread, `stuck` from the thread that called
`checkStuck`. Shells build them outside main-actor context (AGENTS.md);
`KajoShellCore` does it in `nonisolated` functions and uses
`MainActor.assumeIsolated` inside the `views` callback, which does run on
the main thread.

**No oop crosses the surface.** The decision the brief left open: a handle
API. A `ShellProcess` names a Process the VM roots for the host (module 3's
host roots) until `release`; arguments and answers are `ShellValue`s,
copied in and out inside the VM (Strings are allocated by the host call and
rooted until the spawn has them on the new Process's stack). Nothing the
shell holds goes stale when the collector moves objects, and nothing it
holds keeps garbage alive beyond the Processes it has not released.

**Turns.** `runTurn` is module 3's `runMain` with its `TurnStats` made
public as `ShellTurn`. `checkStuck` is module 3's report; the `stuck`
callback gets the Process id and the selector of the method it is in.

**Snapshot.** `snapshot(to:)` spawns `Smalltalk snapshot: path` on a
background worker and waits: module 8c's save, its hold and its stop. It
answers true when the saver's answer was false (it saved; a resumed copy
answers true) and the file exists. A resumed image's event loop registers
its Semaphore with the new shell (`UIEventLoop resumeAfterSnapshot`) and
its view wrappers come back detached (`View resumeAfterSnapshot`).

**Close.** `close` terminates every Process, joins the threads, then waits
(at most `timeoutSeconds`) until no Delay's timer is outstanding, because a
GCD timer firing into a freed VM would write freed memory; past the bound
the VM is leaked, not freed.

## The event queue

The shell posts `ShellEvent`s (kind, the handle of the view it is for, a
value, the time it happened on the uptime clock: CLOCK_UPTIME_RAW, which
`mach_absolute_time`, `CACurrentMediaTime`, CADisplayLink and UIKit and
AppKit event timestamps count). The queue is not a new cross-thread
protocol: a mutex-guarded FIFO in the bridge plus module 3's external-signal
queue. `post` appends under the mutex, reads the registered Semaphore,
unlocks and pushes one external signal for it. The kernel's event loop
registers its Semaphore once (primitive 153, a pending root), which signals
it once for every event already queued, under the same mutex's order;
afterwards every event gets exactly one signal, and the loop takes exactly
one event per wakeup (primitive 154). The Semaphore's count therefore
equals the queue's length at every point a signal is drained, and no
wakeup is lost. Waking an idle worker is the external-signal queue's own
scheduler-lock wake (AGENTS.md: a lock-free push is not a lock-free
wakeup). No model was added: the only new ordering is the registration's
count against the posts, which the mutex serializes, and the rest is the
external-signal queue as module 3 built and tested it.

After posting, the shell runs a turn at once (`ShellRuntime.deliver`): the
turn drains the external signals at its start, the event loop's Process
becomes ready on the main worker and runs, so the handler runs in the
run-loop turn that delivered the event (ADR 0004). If a background worker
drained the signal first, the loop is readied there and `wakeMain`
schedules the turn.

**The scenario.** `ShellBench openScenario:mainAlloc:mainWork:` builds the
window in Smalltalk (a label, a probe View, a Slider, a TextView), installs
a frame action that runs module 7's main-thread load (`mainTick:work:`: 20
two-slot Arrays, every 64th kept in a ring of 256, then 60 000 iterations of
arithmetic, about a quarter of a frame on the M2) and moves the probe, and
a synthetic action that sets the label to the event's number, and starts
the event loop. `startLoad:workers:` forks the background load on one
Process per background worker, forever: storm (module 7's binary trees,
depth 16 built, checked and dropped, a depth-12 tree kept), ring (module
7's fragment kernel, bounded: below), share (module 7's sharestorm). The
display link posts a frame event per refresh and runs a turn; with
`events=1000` a strict 1 ms main-queue timer posts the synthetic events due,
each stamped with when it was due, and runs a turn; the latency is taken
when the label's `set text` reaches the view host. `hog=1` spawns
`ShellBench hog` (an infinite loop, normal priority, main-affine) at the
window's start; the stuck limit is 300 ms; `budget=off` makes every turn one
turn of the window's length less a second (the control). The window is
`seconds` after `warmup`; frames are counted by display-link timestamp
inside it; turn and counter sums run from the window's start as the main
queue saw it.

### The scenarios on the Mac's display

7 background workers, 10 s after 1 s of warm-up, `gc=cm`, module 7's QoS
policy (workers user-initiated, young collector user-initiated, marker
utility), the main thread's frame load 20 allocations and 60 000
iterations per frame, the probe moved by Smalltalk every frame. "Stopped
for others" is ADR 0008's attribution per 10 s; "own" the main worker's
own collections and stops; "acks other" the acknowledgements of other
nurseries' rounds and their mean; P share the fraction of the thread's CPU
on performance cores (`proc_pidinfo` flavor 34; "-" no such thread, 0.00 a
