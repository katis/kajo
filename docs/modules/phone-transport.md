# Module 9d: the phone transport

Status: briefed 2026-11-05, from module 9c's "What 9d needs"
(`docs/modules/developer-ui.md`) and the owner's answer of 2026-11-04 to
the 9b draft ("TCP with Bonjour and a pairing token, development images
only"). Module 9b built the protocol and its Unix-socket transport
(`docs/modules/development-protocol.md`, ADR 0011), module 9c the client in
the image (`DevClient` over primitive 164 and `KajoDev.ClientHost`). 9d
puts a phone at the other end of the same requests.

## What it hides

That the target is on another machine. The tools of the development image
on the Mac connect to a target named in the target picker; whether the
target is the image's own socket, another process on the Mac, or the iOS
shell on the iPhone, the requests, the replies, the events, the debugger
and the files written to the project are the same. The image never sees
an address, a port or a token: `ClientHost` owns them (9c's rule, from the
other side of 9b's trust boundary).

## 1. The target side: the iOS shell serves

- `ShellRuntime.serveProtocol` gains a TCP listener beside the Unix socket
  (`ProtocolServer` takes a listening address as well as a path: one
  accept loop, the same bounded reader, the same first-line token rule,
  the same 64 MiB drop of a client that stops reading). The iOS shell
  serves when launched with `protocol=tcp[:port]` (port 0: the system
  picks), and only a development image serves: a release image refuses as
  9b's does, on any transport.
- **Bonjour.** The serving shell advertises `_kajo-dev._tcp` with the
  device's name; the TXT record carries the image's name, the protocol's
  version and the kernel's version, never the token. Advertising needs no
  permission on iOS; browsing from the Mac uses Network.framework's
  `NWBrowser` (binding code in `KajoDev`, not the VM). Add what
  `Info.plist` needs (`NSBonjourServices`, `NSLocalNetworkUsageDescription`
  if the iOS shell ever browses) and nothing else.
- **The pairing token.** The phone shows its token on screen, large, with
  its Bonjour name and its addresses, while it serves. The token is stable
  per install, kept in the app's own Application Support directory with
  mode 0600 and regenerated by a button on the phone (a new token ends
  every session). The token is never logged, never in a result line,
  never in the TXT record, and the Mac side keeps it in memory or in the
  owner's `~/.kajo/targets` as 9c does. No keychain.
- **Serving on the local network means every host on it can connect and
  try the token.** 9b's constant-time compare holds; add a per-connection
  limit (three failed `session.open` and the connection closes; a listener
  that saw ten failures in a minute stops accepting for a minute and says
  so on screen). Note in the doc that the line is plain TCP on the owner's
  network and that TLS is an owner question (section "Open questions").
- Replies longer than one heap block are already written in pieces (9c);
  the TCP writer must handle a slow link: write in order, never block the
  protocol Process on the socket (the accept thread or a writer thread
  owns the socket, as 9b's server does; measure and say which).

## 2. The Mac side: `ClientHost` and the Swift client over TCP

- `ClientHost.connect` takes a target name or an address: a Unix socket
  path (as today), `tcp://host:port`, or the Bonjour name of a phone the
  browser has found. `targets` lists the Bonjour-found phones with the
  rest (`name TAB address TAB 1/0`), updated as they appear and go
  (`targets.changed` event, so the target picker refreshes). Resolution,
  connect and `session.open` run on the connection's own thread as 9c's
  do; the image waits by callback.
- The Swift client (`KajoDev.Client`, used by the CLI, the MCP server and
  the tests) gets the same TCP transport, so `kajo eval --target <phone>`,
  `kajo debug --target`, `kajo test --target` and `kajo mcp` reach the
  phone. One transport implementation behind both.
- **Reconnect and retry.** A `lost` event fails the pending requests
  today. 9d: `DevClient` reconnects (timer events with backoff: 1, 2, 4,
  8 s, up to a minute, until `close`), opens a new session with the same
  client and package, and **retries the idempotent requests** that were
  pending at the loss (9b made every request a client may send again
  idempotent; the non-idempotent ones, if any, fail as before and the doc
  names them). The target picker shows `connection.lost`,
  `connection.reconnecting`, `connection.open`; the debugger's stopped
  Processes survive the link (they are stopped in the target) and the
  debugger windows refresh from `process.list` on reconnect.
- **Files.** The phone's replies carry `files`; `ClientHost` writes them
  into the project directory given at connect, unchanged from 9c. The
  phone's image is built from `kernel/` plus `apps/Shared/smalltalk`;
  changes made on the phone through the tools land in the Mac's project
  as those packages' files.

## 3. The first remote session, measured

The scripted developer session of 9c (`mode=devsession`) against the phone
instead of the local target, from the Mac mini, over the owner's network,
plus the phone's own frames while it serves:

- **Round trips** per request kind (count, p50, p99, max), with 9c's local
  numbers beside them (small requests 0.4 to 10 ms, `class.hierarchy` 0.33
  s at 2000 classes and 190 KB). The phone's image is the shell image, not
  the 2000-class one; measure the kernel-size hierarchy and say what the
  2000-class one would cost from the measured bytes per second. If a
  request's reply over the link makes the class tree or the selector table
  slow, say whether 9c's on-demand form or a request per package would fix
  it; do not change the tools' default (owner question 2 of 9c).
- **The phone's frames while it serves**: 9a's `scenario=idle` and
  `scenario=ring` rows at 120 Hz with a client making the scripted
  session's requests, against the same rows without a client (9a's
  numbers in `docs/modules/shells.md`). The protocol Process runs each
  request in a Process of its own; the budget rule must keep the frames.
- **The debugger across the link**: an unhandled error on the phone stops
  its Process; the Mac's debugger opens on it, define the method on the
  Mac, retry the send, the phone goes on; the method's file lands in the
  Mac's project. Measured as a step of the session.
- **A dropped link**: kill the connection in the middle of the session
  (close the socket from the test side); the client reconnects, the
  retried requests complete, the stopped Process is still there.
- **Thermal**: record the phone's thermal state per row as 9a did; let it
  cool between rows (bounded waits).

The phone is used **only through `scripts/device.sh`** (extend it for the
serve mode: `just device run <out> mode=serve protocol=tcp seconds=N
scenario=...`, its console streamed to the Mac as today); the Mac side
through `scripts/mac-shell.sh` with a `target=` option. The Mac mini is on
the owner's network; the phone must be on the same one. If the phone
cannot be reached over the network, change no network, Wi-Fi or system
setting: measure the transport Mac to Mac over TCP (loopback and the
Mac's own LAN address, `kajo run --protocol tcp` as a second target) and
report the phone part as not done, with the reason seen.

## Rules

- The token never enters the image, is never written by the target, never
  appears in a log, a result line or a TXT record.
- A release image serves on no transport. A development image serves TCP
  only when asked (`protocol=tcp`), never by default.
- Everything received over TCP goes through 9b's bounded reader and 9c's
  `ClientHost.check`; a bad line is a reply or an event, never a trap.
  `just fuzz protocol` must cover any new parsing (the TXT record, the
  address forms, the targets file's new lines).
- No tool logic in Swift: Bonjour browsing, TCP, reconnect timing are
  transport, in `KajoDev`; what to show and when to retry which request
  is `DevClient`'s, in Smalltalk.
- The interpreter is not touched; `just arc-check` and the bench A/B hold.

## Deliverables

- `ProtocolServer` over TCP with Bonjour advertisement, the failure
  limits, the token on the phone's screen; the iOS shell's `protocol=tcp`.
- `ClientHost` and `Client` over TCP with Bonjour browsing and
  `targets.changed`; `DevClient` reconnect and retry; the target picker's
  states.
- `scripts/device.sh` serve mode, `scripts/mac-shell.sh target=`, and the
  measurement tables of section 3 in the as-built doc.
- Tests: the server over TCP on loopback with the token rule and the
  failure limits, the client's reconnect and retry with a fake link that
  drops, Bonjour browsing against a listener the test starts, the targets
  file's address forms; the fuzz target extended.
- The as-built doc replaces this file; ADR 0011 gets a Built (9d) note;
  `docs/CONTEXT.md` terms.

## Not in this module

TLS or any encryption of the link (owner question); USB tunnelling
(devicectl forwards no ports); the developer UI on the phone; serving from
the Mac shell to another Mac's tools beyond what the loopback and LAN
tests exercise; the host saving the image while Processes have frames and
old space growing at the VM's end (owner-decided, a follow-up of its own).

## Open questions this module will put to the owner

Whether the line needs TLS on the owner's network; whether the token
should expire; whether a phone should accept more than one session at a
time; whether the phone should ever serve without the launch argument (a
switch in the app).
