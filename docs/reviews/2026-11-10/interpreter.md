# Review: interpreter at d78afcc

## Summary
I read the bytecode verifier and opcode table (`Loader/BytecodeVerifier.swift`, `Interpreter/Opcodes.swift`) and the dispatch loop (`Dispatch.swift`) whole, along with the send, return and primitive paths (`Send.swift`, `Special.swift`, `Primitives.swift`, `InterpreterState.swift`), `MethodBuilding.swift` and `fuseBytecodes`, and `verifyHeapMethod`. I also read the image loader's object-model rules (`ImageFile.swift` whole and the frame and queue half of `SavedProcessRules.swift`), and the frames, Contexts, non-local return and `terminateTo:` code in `ObjectModel/Frames.swift`. On the Processes side I read `Closures.swift`, `StackGrowth.swift`, `Workers/Poll.swift`, `Processes/Debugging.swift`, `ProcessPrimitives.swift` and the termination and Semaphore half of `Scheduling.swift`. I checked each against the kernel methods that use it and against `ExtremeIntegerTests` and `DevProtocolTests`. The most serious finding is that the read-only bit is the only thing that protects a verified method's bytecodes and literal Array, and any Smalltalk program can clear it with primitive 93 (`beWritable`). After that it can rewrite the bytecodes of a running, pinned method and run code the verifier never saw, which corrupts memory. The next is that suspending a Process that waits on a Semaphore (`process.suspend`) and then proceeding it returns from `wait` without a signal, which breaks `critical:` mutual exclusion. A test primitive (39) is still reachable from a development image and reads weak slots without the keep-alive barrier. Two lower findings concern primitive 156's frame-position assumption and interrupts that are lost across a save. I did not get to the kasm parser and assembler, `Image.swift`'s build half, `Headless.swift`, `Run.swift`, `Worker.swift`, `VM.swift`, `Safepoint.swift`, `SavedProcesses.swift`, `External.swift`, or the random-program generator and fuzz entries. I ran nothing.

## Findings (ranked, most severe first)

### F1. Primitive 93 clears the read-only bit of a method's bytecodes and literal Array, so a program can rewrite verified code and run bytecodes the verifier never saw
- Severity: critical   Confidence: confirmed (traced by reading; not run)
- Where: `Sources/KajoVM/ObjectModel/ObjectModelPrimitives.swift:100-105` (case 93 refuses only a receiver of a sealed class; ByteArray and Array are not sealed, `Interpreter/ObjectModel.swift:77-119`). The way in is `kernel/Methods/CompiledMethod.class.st` `bytecodes` / `literals` (`slotAt:` 1 and 2, primitive 117, `KernelPrimitives.swift:46-53`) and `Object>>beWritable` (`kernel/Objects/Object.class.st:328`). The stores that then succeed are `Special.swift:72-79` (the `at_put` tier), `Primitives.swift:93` (primitive 2), `LongBytes.swift:383` (primitive 38) and `Interpreter/InterpreterState.swift:390-392` (`become:` refuses only read-only objects).
- Invariant: AGENTS.md says "Class, Method and MethodDict are sealed from Smalltalk ... or a verified method's bytecodes could be rewritten at run time". `MethodBuilding.swift:1-10` makes the bytecodes and literal Arrays "pinned for good ... and read-only", because the interpreter caches raw pointers into them. The image loader refuses any method whose bytecodes or literals are not read-only (`ImageFile.swift:366-367`), and `LiveCompileTest>>testMakeVerifiesAndCopies` asserts `m bytecodes isReadOnly`. The dispatch loop trusts every operand it reads: `push_temp n` reads `r.fp[1+n]` with no bound (`Dispatch.swift:22-25`), and `push_closure` reads `literals[lit]` as a block method with no check (`Closures.swift:22-24`).
- Path that breaks it: in a development image run `| b | b := (Foo >> #bar) bytecodes. b beWritable. b at: 1 put: 0. b at: 2 put: 255. b at: 3 put: 13`. That turns the code into `push_temp 255; return_top`, with temp 255 far outside the frame, and the next `Foo new bar` reads a word past the frame or stack segment and answers it as an oop. `store_temp 255` (`r.fp[256] = …`) writes past the frame instead. On the literal side, `(Foo >> #bar) literals beWritable; at: k put: 3`, where k is a `push_closure` literal, makes `pushClosure` call `methodFlags` on a SmallInteger and build a closure whose `method` is not a method. `activateClosure` then reads a body through `stateWord` of an immediate. Either way the result is memory corruption, or a signal 11 in release. A release image does not stop this: primitive 93 is not release-gated, and an app's own Smalltalk can do it.
- Neighbours that have it right: Method, MethodDict and Class themselves are sealed, so 93 refuses them. Primitive 2 refuses Strings and Symbols outright, and the loader checks the very property that 93 lets a program undo.
- Test that would fail today: a kernel test (`ReadOnlyTest` or `LiveCompileTest`) that runs `(Object >> #yourself) bytecodes setReadOnly: false` and `(Object >> #yourself) literals setReadOnly: false` and asserts that each signals the primitive's error and the object is still `isReadOnly`.
- Fix sketch: primitive 93 refuses to clear the bit on any object that is pinned for good. Every method part, literal and Symbol is pinned for good by `MethodBuilding` or `Image`. Alternatively, give methods' parts a separate "frozen" header bit that no primitive clears. List every path that clears read-only (93 only, by grep) in the same commit. Consider also refusing `become:` of a pinned-for-good object.

### F2. Suspending a Process that waits on a Semaphore, then proceeding it, returns from `wait` without a signal, which breaks `critical:` and the other Semaphore protocols
- Severity: high   Confidence: confirmed (by reading)
- Where: `Sources/KajoVM/Processes/Debugging.swift:166-172` (`interrupt`, kind 2 on a waiting Process: unlinked from the Semaphore, made ready, `debugStopAfterSend`). `kernel/Processes/Process.class.st:72` (`stopForDebuggerAfterSend` goes on after the send once the debugger proceeds). `kernel/Processes/Semaphore.class.st:13` (`critical:`: `self wait. ^ aBlock ensure: [self signal]`). `kernel/Development/Debugger.class.st:86` (`process.suspend` asks `primInterrupt: 2`).
- Invariant: a `wait` answers only after a matching `signal`. The design says "the Process goes on as it was" after a stop (`runInterrupt`'s comment, `Debugging.swift:179-182`). For a waiting Process, "as it was" means still waiting.
- Path that breaks it: Process B holds `m := Semaphore forMutualExclusion` inside `m critical: [...]`, and Process A blocks in `m critical:`. A client sends `process.suspend` for A, and A is unlinked and stops in `stopForDebuggerAfterSend`. The client then sends `process.proceed`, and A returns from `wait` and enters the critical block while B is still inside. When both leave, `excessSignals` is 1 too high for good, so two Processes can enter from then on. The same applies to `Mutex`, `Monitor`, `SharedQueue` (`next` finds an empty queue) and `Delay` (it returns early). Terminate (kind 1) is fine, because it unwinds from after the `wait` and the `ensure:` was never entered.
- Neighbours that have it right: terminate's path. The debug stop of a running Process (kind 2 at a poll) rewinds the pc to the send, so proceeding runs the send again.
- Test that would fail today: in `DevProtocolTests`, next to the busy-Process suspend test (`DevProtocolTests.swift:398-406`), make Process A wait on a `Semaphore new` that nobody signals. Suspend and proceed A, then assert that A is still waiting (its state, or that a flag it sets after `wait` stays unset). A kernel variant can use `critical:` and count entries.
- Fix sketch: for a waiting Process, record the length of its `wait` send and resume it with the pc rewound to that send (`debugStop`, not `debugStopAfterSend`), so proceeding waits again. Alternatively, have `stopForDebuggerAfterSend`, when it was asked for a wait, re-send `wait` to the Semaphore it was taken from. Pharo re-waits a suspended waiter for the same reason.

### F3. Test primitive 39 (`slowPeek:`) is reachable from Smalltalk and reads any slot, weak ones included, without the keep-alive barrier
- Severity: high (the effect is a lost object; it is reachable only by a program that defines a `<primitive: 39>` method in a development image)   Confidence: likely
- Where: `Sources/KajoVM/Interpreter/Primitives.swift:51` dispatches 39 in every build. `Sources/KajoVM/YoungCollection/Mutator.swift:103-117` reads `addr.pointee.load` with no `keepAliveRead`, no sealed check and no hazard slot. `Sources/KajoCompiler/Compiler.swift:859` and the make primitive (`LiveMethods.swift:155`) accept any primitive from 1 to 255.
- Invariant: AGENTS.md says "a new slot-reading primitive goes through `keepAliveRead`" (collectors review, `docs/modules/collectors-review.md` table). Test-only machinery belongs behind test switches.
- Path that breaks it: `Object compile: 'peek: i <primitive: 39> ^ nil'`, then `holder slot: (aWeakArray peek: 1)` while a cycle marks, with the referent held only weakly at the snapshot. The referent is swept under a live reference, which is the bug the collectors review fixed for `at:`, `instVarAt:` and `slotAt:`. Primitive 39 also reads slots of sealed objects, though 117 already allows that. The `peekGate` wait is 0 by default, so it does not hang.
- Neighbours that have it right: primitives 1, 91, 117 and 96 call `keepAliveRead`.
- Test that would fail today: the marking suite's weak keep-alive test with primitive 39 in place of `at:` (`noWeakKeepAlive` shows the shape).
- Fix sketch: refuse 39 unless a VM test switch is on (as `superFromReceiverClass` and the other switches do), or remove it from `primitive(_:)` outside `-enable-testing` builds. In any case route its read through `keepAliveRead`. Also have the make primitive refuse primitive numbers that the table marks test-only.

### F4. Primitive 156 (`primResend:`) assumes the running frame's fp is the caller's send-receiver slot, and frames made by interrupts break that
- Severity: low   Confidence: possible
- Where: `Sources/KajoVM/Processes/Debugging.swift:288-325` (`resend`: `rfp` from `frameFP(rh)`, `sp := rfp + n`, `pc := start` of the send that ends at `returnPC`).
- Invariant: after a resend the frame's operand depth at `start` equals the verifier's traced depth (the saved-frame rules check it, `SavedProcessRules.swift:356-372`, and `maxStack + 1` is the reserve).
- Path that breaks it: the frame that `runInterrupt` / `markedSend` creates (`stopForDebugger`, `terminateUnwinding`) has fp = sp + 1 above the caller's operands, not at a send's receiver slot. When the caller was rewound to a send start, `sendEnding(returnPC)` finds the instruction before it, which is a send whenever two sends are adjacent. Code that runs inside that stop, such as the debugger's evaluate-in-frame or any Smalltalk with `thisContext`, can call `ctx restartSendWith:` with operands of the right size. The resend then leaves one more operand than the trace at `start`. The debugger's own `restart:` refuses this through its selector check, but `restartSendWith:` is public. The stack stays inside `maxStack + 1` plus the segment slack, so the visible results are wrong depths and a save that the loader then refuses.
- Neighbours that have it right: frames made by sends, DNU, `perform:` and closure `value` all have fp at the receiver slot.
- Test that would fail today: a kernel test that interrupts a Process at `a foo bar` with kind 2 and resends `foo` from inside the stop, then saves. Loading the saved image is refused with "pc … traced …".
- Fix sketch: in `resend`, require `rfp == sfp + depthBefore(start)`, the traced depth at `start` minus `n` plus `sfp` offsets. A cheaper rule is to refuse when R's context word carries the discard or cascade marker, since the VM made that frame.

### F5. Pending interrupts and terminate requests are not saved, so a Process asked to unwind or stop just before a save resumes as if nothing was asked
- Severity: low   Confidence: likely
- Where: `ProcessRecord.interrupt` and `terminateRequested` (`Scheduling.swift:155-159` and `236`) live only in the host-side record. Nothing in `Processes/SavedProcesses.swift` writes them (grep finds no `interrupt` or `terminateRequested`).
- Invariant: "Every running Process leaves its worker at a poll ... registers exact" (save-hold model). A Process's pending interrupt is part of what it will do next.
- Path: `p terminate` from another Process sets kind 1 on a ready Process, and `Smalltalk snapshot:` runs before p resumes. The resumed image's p continues its work. After `unwindBudgetMs` its terminator cuts it off without running its `ensure:` blocks, and counts a cut-off. A `process.suspend` asked before a save is silently dropped.
- Test that would fail today: an image-processes test that interrupts a ready Process, saves with `--snapshot-at`, loads, and asserts that the Process's `ensure:` ran.
- Fix sketch: write the interrupt kind into a Process slot (or the saved chunk's pair) at save and restore it into the record on load. Alternatively, have the save's hold refuse until pending interrupts have run.

## Checked and sound
- Verifier operand bounds: temp, literal and ivar operands are checked against the shape for plain and `ext` forms (`decodeInstruction` ORs `hi << 8`). `push_new_array` is bounded by `maxSlots`. The vector-slot temp index is checked, and the slot is checked at run time by `hasSlot`/`canStore`. A send's literal is a Symbol of the send's arity. A closure's literal is a block method with matching copied values, and its needsHome flag is checked against the enclosing shape.
- Jump targets: the target must be an instruction start (`at[t]`), so a jump cannot land on an `ext` instruction's opcode or operand. A jump to a fused pair's second half runs the plain second instruction, as designed.
- Fused opcodes: the second part must follow as a plain, unextended instruction of the named opcode (`ins[k+1].op == second, fused == nil, length == second.length`), and it is verified as an instruction in its own right. Every fused case in `Dispatch.swift` reads its operands at the right fixed offsets. When a fast path does not apply, each fused case runs the first part alone and leaves pc at the intact second part (push_int+add/sub, add/sub+store_temp, the compare+jump family through `specialSend` with length 1). `fuseBytecodes` never fuses extended or already-fused instructions.
- `ext` before a fused or non-extensible opcode does not decode (fused opcodes are not `isExtensible`).
- Stack-depth tracer: one depth per instruction, no underflow, no fall-off. Transient words are counted for `store_ivar`/`store_tv_slot` (2) and `nonlocal_return` (2). The unary-DNU word fits the one-word reserve in `activate` and `activateClosure` (`maxStack + 1`). `runInterrupt` pushes into that same reserve, and every way into it (a poll at a send, after a send, at a `wait`) is at or below `maxStack`.
- Super sends from a method whose class has a nil superclass go to `doesNotUnderstand` (`Special.swift:295`).
- Primitive numbers: `prim < primitiveTableSize`, and negatives are refused by `int()`. Every primitive I read checks `c.argc` before reading arguments. `Machine.argument` has a precondition.
- The empty-method case: the verifier accepts empty bytecodes, but `verifyHeapMethod` refuses empty bytecodes with no primitive and empty block methods. A failed primitive with no bytecodes is `primitiveFailed` in `primitiveSend`, `primitiveFailure` and `markedSend`. Primitive 85 requires primitive 0.
- `verifyHeapMethod`: header slots are small non-negative integers. Flags are a known set, and block and method header rules apply. Bytecodes and literals are checked for kind and size before reading. The source-map last literal must be a ByteArray. The selector's arity must equal argc. The method class must name the class index. Block literals are verified recursively to depth 64.
- Image loader: every slot read is guarded by `slots`/`isA`. Method dictionary entries must be Symbols mapping to methods of that class whose selector equals the key. Closures must fit their block method. The method table must equal the heap's methods, and every method must be pinned for good with read-only bytecodes and literals. Class pools must be read-only Arrays.
- Saved frames: fp is recomputed from the method, the block's closure and receiver checked, the context word an empty word, a marker in the known set or a Context naming the frame back. The depth is checked at the top pc and at every caller pc (with the discard and cascade cases). pc -1 is checked with fork's layout. Links are SmallIntegers that decrease.
- Semaphore and ready lists are checked for acyclicity, membership and states.
- Stack growth copies `[0, sp]`, updates the record under the lock and the interpreter's base and end, and every caller then calls `restore`, which rebuilds the registers from offsets.
- Contexts: `liveFrame` checks the class, the Process, `h + context <= sp` and that the frame's word names the Context. `tempAt:put:` on a live frame is bounded by the frame's temp count. `terminateTo:` checks that the target is live and below and that the callee chain reaches it. Non-local return to a dead home sends `cannotReturn:`. Unwind marks between the block and its home send `aboutToReturn:through:`.
- The inline `at:` (Array only, `k < count`), `specialFastPath` `at:`/`at:put:`/`size` (Array and ByteArray, read-only checked, long ByteArray `size` sent) and `isNil`/`notNil` cannot read past an object. WeakArray takes the primitive path, which has the barrier.
- Primitive 2 and 38 refuse read-only receivers. Primitive 2 also refuses String and Symbol.
- Poll: the first budget check of a slice never preempts (`freshSlice`), so neither livelock form occurs. The save hold requeues at a poll with the pc rewound. Interrupts are read under the scheduler lock.
- `interrupt` refuses a Process on its first slice (pc -1, not running).
- `waitSemaphore` honours a pending interrupt or terminate before it waits.
- `ExtremeIntegerTests` covers 1, 2, 3, 6, 7, 14, 15, 25, 38, 40-57, 73, 77, 91, 92, 101, 102, 116-118, 124, 125, 127, 128, 132, 134, 136, 152 and 167-170. The integer-taking primitives I found outside the list are safe by reading: 155 (equality with 1 or 2), 158 (`0...7`), 29 (passes the value to the host hook) and 39 (bounds checked; see F3).
