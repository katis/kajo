## Summary

I did not read `Numbers.swift`, `Frames.swift`, `Closures.swift`, `Symbols.swift`, `ReadOnly.swift` beyond the setter, most of `LongBytes.swift`, the rest of `LiveClasses.swift` (145 to 147 bodies), `CLI.swift`, `Development.swift`, `Stats.swift`, the fuzz target, and most of the docs and tests named in the brief (I read the file-primitive test's link cases). The most serious finding: primitive 93 lets any program clear the read-only bit of a made method's bytecodes ByteArray or literal Array (both reachable through `slotAt:`), after which ordinary `at:put:` rewrites verified code: the sealing of Method is bypassed and the interpreter runs unverified bytecodes. The transport has an accept loop that dies for good on any `accept` error and no cap on unauthenticated connections, a write-after-close race on both sides that can put one session's line on another descriptor, a quadratic JSON reader reachable before the token, and server-side closes that never tell the image the session ended. The new directory creation of 148 reads sound against links; 148 itself is not serialized, so concurrent writes of one file can tear it. Nothing was built or run.

## Findings (ranked, most severe first)

### F1. `setReadOnly: false` (primitive 93) un-protects a verified method's bytecodes and literal frame, so verified code can be rewritten at run time
- Severity: critical   Confidence: confirmed (by reading; not run)
- Where: `Sources/KajoVM/ObjectModel/ObjectModelPrimitives.swift:100-105` (93 checks only that the receiver's own class is not sealed); the protection it defeats is made in `Sources/KajoVM/Loader/MethodBuilding.swift:62-64,117-123` (`readOnlyPinned` on the bytecodes ByteArray and the literal Array); the path to them is `KernelPrimitives.swift:46-53` (117 `slotAt:` reads any slot of a sealed object, whose comment says "reading cannot break what sealing protects (bytecodes, literal Arrays and Symbols are read-only...)").
- Invariant: AGENTS.md: "Class, Method and MethodDict are sealed from Smalltalk ... or a verified method's bytecodes could be rewritten at run time. Slot reads through `slotAt:` are allowed ... a read rewrites nothing"; 143 makes "its literal frame and every literal it made read-only" before any Process sees it (`LiveMethods.swift:22-30`). The read-only bit is what keeps the read harmless.
- Path that breaks it: `bc := (Object >> #printString) slotAt: <bytecodes index + 1>. bc beWritable. bc at: 1 put: <any opcode byte>`. ByteArray is not sealed, so 93 clears the bit; every store path checks only that bit, so `at:put:` (or primitive 38, `encode:at:`) then writes. The next activation (or a running frame, since the body is pinned and read in place) executes bytes the verifier never saw: temp/ivar/literal indices past their bounds, jumps out of the method, a `push_closure` on a non-method. Same with the literal Array (`(m slotAt: <literals+1>) beWritable; at: k put: 42` turns a block literal into a SmallInteger read as a CompiledMethod, or swaps a selector for one of a different arity so the verifier's stack depth no longer holds). Works in a release image too (93 has no release check), and from any paired client or agent via `evaluate`.
- Neighbours that have it right: `instVarAt:put:` and `shallowCopy` refuse sealed receivers; primitive 2 and 38 refuse Strings/Symbols outright, so a Symbol made writable still cannot be changed; the loader re-verifies on load. Nothing protects the non-sealed objects a sealed one owns.
- Test that would fail today: a kernel or `ReadOnlyTests` case: make a method with 143, read its bytecodes with `slotAt:`, `setReadOnly: false` must fail (and `at: 1 put:` must still send `modificationForbiddenAt:value:`); the same for the literal Array and a literal String.
- Fix sketch: 93 refuses to clear the bit on an object pinned for good (every object 143, the image build and interning make read-only is also pinned for good), or a separate sticky "frozen" header bit that no primitive clears. Audit `become:`/`becomeForward:` on those objects in the same commit.

### F2. The protocol listener's accept loop ends for good on any `accept` error, and an unpaired peer can drive it there
- Severity: high   Confidence: confirmed (EMFILE path), likely (ECONNABORTED)
- Where: `Sources/KajoDev/Server.swift:220-253` (`if c < 0 { if errno == EINTR { continue }; return }`), with `readLoop` (`255-290`) giving every accepted connection its own `Thread`, no cap on connections, no time limit before `session.open`, whitespace-only lines kept open (`294`), and up to 16 MiB buffered per connection before the token is checked (`278`, `RequestLimits.lineBytes`).
- Invariant: docs/modules/phone-transport.md and the file comment: "limits for a network where every host may try the token"; the listener pauses for a minute and then serves again.
- Path that breaks it: any host on the LAN (no token needed) opens connections to the phone's or Mac's TCP port and sends nothing. Each costs a descriptor and a thread. When the process reaches its descriptor limit (256 soft by default for an app), `accept` returns `EMFILE` and the accept thread returns: the listening socket stays open, so later clients (the developer included) complete the TCP handshake into the backlog and then hang, after the attacker leaves too, until the app is relaunched. A connection reset while in the backlog (`ECONNABORTED`) ends the loop the same way. Before that point, a few hundred such connections each holding a 16 MiB partial line cost gigabytes on a phone (jetsam). The token rule and the 10-failure pause do not see any of this (no `session.open` is ever sent).
- Neighbours that have it right: `readLoop` and `Client.readLoop` retry `EINTR` and treat other errors as the end of one connection, not of the service.
- Test that would fail today: `TransportTests`: lower `RLIMIT_NOFILE` in a child or open descriptors until `accept` fails, then free them and assert a new client still gets a session; and a test that N idle unauthenticated connections are closed after a bound.
- Fix sketch: on `EMFILE`/`ENFILE`/`ECONNABORTED`/`ENOBUFS` log, count, back off briefly and continue; cap unauthenticated connections (close the oldest), close a connection that has not sent `session.open` within a few seconds, and bound the pre-session line to a few KiB.

### F3. A write queued after `close` lands on a closed descriptor that may already be another connection's
- Severity: high   Confidence: likely (window is small; the shape is AGENTS.md's "a descriptor closed twice closes someone else's")
- Where: `Sources/KajoDev/Server.swift:525-570` (`Connection.send` checks `closed` under the lock, unlocks, then `queue.async { write(fd) }`; `close` sets `closed`, unlocks, then `queue.async { close(fd) }`); `Sources/KajoDev/ClientHost.swift:473-502,559-567` (`send` reads `fd` under the lock, unlocks, then `write(f)` enqueues; `release` sets `fd = -1`, drains the queue with `queue.sync {}`, closes `f`).
- Invariant: the comment at `Server.swift:564-566`: "the fd is closed after them, so it is never reused under one"; ClientHost's `release`: "closed once the queued writes are done".
- Path that breaks it (server): a VM thread in `deliver` calls `c.send(line)` for an event; it passes the `closed` check and unlocks. The connection's reader sees EOF (or `replaceToken`/`dropConnections` runs) and calls `close()`, which enqueues the `close(fd)` block first. The send's write block is enqueued after it and runs on the closed number. Meanwhile the accept thread may have accepted a new connection that got the same descriptor number: the old session's event or reply (transcript, results of an `evaluate`, inspected values) is written to the new peer, which can be an unpaired one. (Client side: the VM thread's `send` takes `f`, the connection thread's `release` closes it with an empty queue, the late write goes to whatever reused the number, a file primitive's descriptor or a Bonjour resolver's.)
- Neighbours that have it right: `ProtocolClient.write` holds its lock across the write and `close` takes the same lock before closing (`Client.swift:139-151,194-223`).
- Test that would fail today: hard to make deterministic; a test switch that sleeps between the unlock and the `queue.async` in `send`, with a close and an accept in between, then asserts the new connection receives nothing.
- Fix sketch: decide `closed` inside the queue block (the close block sets a queue-owned flag; write blocks check it), or enqueue the write while holding the lock so its order against the close block is the lock's order; on the client, hold the lock across reading `fd` and enqueueing.

### F4. When the server ends a connection, the image never hears `session.close`: every "New token", dropped link and backlog drop leaks the DevSession
- Severity: medium   Confidence: confirmed
- Where: `Sources/KajoDev/Server.swift:283-289` (`if conn.isOpen { post(... "session.close" ...) }` after the loop), with `isOpen` = `open && !closed` (`510-515`); every server-side close sets `closed` first: `replaceToken` (`393-399`), `dropConnections` (`403-408`), the 64 MiB backlog drop in `send` (`527-531`), `stop` (`467-485`). Kernel side `kernel/Development/DevProtocol.class.st:182-188` removes a session only on `session.close`.
- Invariant: phone-transport.md: the "New token" button "ends every session"; a session is the image's `sessions at: conn`.
- Path that breaks it: a developer pairs, inspects objects (the session's handle table holds them), presses New token on the phone. `replaceToken` closes the connection; the reader ends; `conn.isOpen` is false because `closed` is true, so no `session.close` is posted. The image keeps the DevSession and everything its handles hold, forever (connection ids are never reused, so it is only a leak, not a confusion). Every reconnect after a dropped Wi-Fi link that the server noticed by its own close adds one.
- Neighbours that have it right: a client-initiated close (EOF with `closed` false) posts it.
- Test that would fail today: `DevProtocolTests`: open a session, `replaceToken`, then ask the image (a second session, or a kernel probe) how many sessions it holds; expect 1.
- Fix sketch: track "the image was told of an open session" separately from `closed` (e.g. read `open` alone) and post `session.close` whenever `open` was true.

### F5. The JSON reader's duplicate-key check is quadratic per object; reachable before the token and from a target
- Severity: medium   Confidence: confirmed
- Where: `Sources/KajoDev/JSON.swift:124` (`fields.contains(where:)` per member), with limits from `Request.swift:73-76` (16 MiB, 4096 members per object, any number of objects) and `ClientHost.swift:357-361` and `Client.swift:71` (64 MiB, 1 048 576 members per object).
- Invariant: the file comment: "whatever a connection sends is a value or a refusal, never a trap or an unbounded cost".
- Path that breaks it: an unpaired peer sends one 16 MiB line, an array of about 400 objects of 4096 distinct short keys: about 3 x 10^9 string comparisons on that connection's thread before the token is looked at; many connections in parallel occupy every core. Against the client side, a malicious or spoofed target (Bonjour names are not authenticated, F-notes) sends one object of a million distinct keys: about 5 x 10^11 comparisons, the client's reader thread (the tools' connection, `kajo mcp`) effectively hangs.
- Neighbours that have it right: every other bound in the reader is linear (depth, elements, string bytes).
- Test that would fail today: a `DevProtocolTests` case timing `parseRequest` on such a line against a CPU budget (as the suite's other CPU bounds).
- Fix sketch: a `Set<String>` of the object's keys (or sort-and-compare at the end); and bound the pre-session line (F2).

### F6. Primitive 148 is not serialized and its temporary file has a fixed name: two writes of one file can tear it
- Severity: medium   Confidence: likely
- Where: `Sources/KajoVM/ObjectModel/LiveClasses.swift:863-907` (not in a stop, unlike 145 to 147; `tmp = path + ".kajo-tmp"`; `writeFile` first `unlink`s `tmp`).
- Invariant: the comment at `871-873`: "the file is replaced whole (written beside it and renamed over it)".
- Path that breaks it: two Processes on two workers write the same file (two protocol requests each in its own Process, both ending in a write-back of the same class file). A creates `tmp` and writes; B's `unlink(tmp)` removes A's name, B creates a new `tmp` and starts writing; A's `rename(tmp, path)` moves B's partly written file into place and A answers true; B's rename fails (ENOENT), B answers a failure. The file holds B's partial text while the writer that reported success wrote something else. With a String cut mid-scalar the next read (149) also refuses it as invalid UTF-8.
- Neighbours that have it right: `PairingTokenStore.renew` has the same shape but one writer; 145 to 147 run in a stop.
- Test that would fail today: a Swift test running two writers of one path in a loop on two workers and checking the content is one of the two whole texts.
- Fix sketch: a unique temporary name (`mkstemp`-style suffix, still `O_EXCL | O_NOFOLLOW`, never unlinking a name it did not create), or a per-VM file lock around 148.

### F7. The image chooses the client's project directory, so Smalltalk can write and remove files outside the directory the file primitives are confined to
- Severity: medium   Confidence: likely
- Where: `Sources/KajoDev/ClientHost.swift:246-263` (`connect`'s fourth argument, any String, becomes `ClientConnection.project`) and `325-331` (every `ok` reply's `files` applied there with `ProjectWriter`); `Sources/KajoDev/Project.swift:54-88`.
- Invariant: vm-teardown.md and LiveClasses.swift: the file primitives are bounded to the directory the host opened (`--sources`), "no component leads out"; Project.swift: a remove "must never reach outside the project or remove a directory that is not empty" (the brief).
- Path that breaks it: in a development image, a program (or a paired client's `evaluate`, or an agent) calls primitive 164 `connect` naming its own `local` target (the host holds that token) with `project: '/Users/me/Somewhere'`, then sends requests whose replies carry `files` (the image can change `DevSession` live). The host writes `X.class.st` files there, creates one-level tag directories, and removes `.class.st`/`.extension.st` files, in any directory the user can write. `ProjectWriter` also `removeItem`s a path named `Foo.class.st` that is a directory, recursively, because `fileExists` is true for directories (`71-73`).
- Neighbours that have it right: `sourcesPath` confines 148/149 to one host-chosen root; the CLI's and MCP's `--project` come from the person.
- Test that would fail today: a `ClientHostTests` case: `connect` with a project directory the host did not configure must be refused (or the call must not write there); a `ProjectWriter` remove of a directory named `A.class.st` must refuse.
- Fix sketch: the host decides the project directory (a setting or an allowlist of the targets' configured projects) and ignores the image's argument or checks it against that; `ProjectWriter` removes only regular files and links (`lstat`), never directories.

### F8. `ProtocolClient` reads unbounded lines and closes its descriptor while the reader may still use it
- Severity: low   Confidence: likely
- Where: `Sources/KajoDev/Client.swift:60-82` (no line bound: `buffer` grows until a newline; ClientHost has the 64 MiB discard rule, this reader does not) and `194-223` (`close` waits at most 1 s for the reader, then `Darwin.close(fd)` even if it has not ended).
- Path: a target (or a spoofed Bonjour name) sends bytes without a newline: `kajo eval`/`kajo mcp` grow without bound. Separately, a reader still inside `parseJSON` of a long reply (or an `onEvent` callback) past the 1 s wait finds its descriptor closed and possibly reused (MCP reconnects at once via `connected()`), and reads someone else's bytes.
- Fix sketch: the same 64 MiB discard rule as `ClientConnection.readLines`; `close` waits for the reader without a bound after `shutdown` (shutdown makes `read` return), or the reader closes the descriptor itself.

### F9. Primitives 154 and 160 dequeue before they allocate: a heap-full failure loses the event or the request
- Severity: low   Confidence: confirmed
- Where: `Sources/KajoVM/Shell/ShellPrimitives.swift:114-118` (`bridge.take()` then `eventArray`), `132-142` (`takeRequest()` then `newString` / `allocate`).
- Path: under memory pressure the allocation answers `.none`, the primitive fails, and the element is gone from the queue while the Semaphore's signal was consumed. A lost request is never answered (the client waits for its timeout); a lost `lost` or `line` event leaves `DevClient` waiting.
- Fix sketch: allocate first and dequeue after, or put the element back at the head on failure.

### F10. A `ShellProcess` used after `release` reads whatever reused the entry
- Severity: low   Confidence: possible (needs a host bug; none found in the code read)
- Where: `Sources/KajoVM/Shell/Shell.swift:262-266,494-502`, `Sources/KajoVM/Workers/VM.swift:261-287` (`state(of:)` loads `ProcessLayout.state` from the oop with no class check and force-unwraps `ProcessState(rawValue:)`).
- Invariant: shells.md: no oop crosses the host surface; `ShellProcess` is a public `Sendable` value that does carry one and outlives `release`.
- Path: host code keeps a copy of a `ShellProcess`, releases it, the Process is collected and its entry reused; `state(of:)` reads a slot of an unrelated (maybe smaller) object or traps on the unwrap.
- Fix sketch: keep the host's roots in a table keyed by a generation-checked handle and have every `ShellProcess` call validate it (or check `isUsedReference` and the Process class inside `host {}`).

### Notes (not ranked as findings)
- Plain TCP and an unauthenticated Bonjour name mean a LAN host that advertises a target's instance name (for instance while the phone's app restarts and gets renamed "(2)") receives the token the Mac's host sends in `session.open`; the owner chose plain TCP now and PSK-TLS later (phone-transport.md). Recorded because the "never written to a file" rule does not cover it.
- Anyone on the LAN can keep the listener paused indefinitely by sending ten wrong tokens a minute; by design.
- `PairingTokenStore.renew` ignores a failed or short `write` and a failed `rename` and answers the new token anyway (`Serving.swift:77-90`), so the next launch serves the old one; `load` does not check the file's mode.
- `ClientHost.run` timestamps a reply's `line` event after `ProjectWriter.apply` (file writes), not when the line was read (`ClientHost.swift:332`), against the "time it happened" rule.
- `ShellBridge.post` may signal a Semaphore that a concurrent re-registration just unrooted; `drainExternal` refuses a reused entry that is not a Semaphore, so the worst case is a spurious signal to another Semaphore that reused the entry.

## Checked and sound
- 148/149 path rules (`sourcesPath`): empty, `.`, `..`, NUL and absolute paths refused; root resolved; every parent resolved and prefix-checked against the resolved root (a sibling `root2` cannot pass `realRoot + "/"`); last component that is a link outside, dangling, or the root itself refused; reads open the resolved path `O_NOFOLLOW`; a write replaces a link inside rather than following it; reading a directory fails cleanly (EISDIR from `read`).
- 148's new `creatingDirectory`: only when the file's own directory is the one missing component; the grandparent resolved and checked inside; `mkdirat` on a descriptor opened `O_DIRECTORY | O_NOFOLLOW` of the resolved grandparent; a dangling link in the tag's place makes `mkdirat` fail; an existing tag directory that is a link is refused by `lstat`; two missing components refused; no refusal after the `mkdir` inside `sourcesPath` (so no stray directory on a refused path except a failed rename). A link planted between `realpath` and `open` needs another local process; a Smalltalk program has no primitive that makes links.
- A write over an existing directory fails at `rename` and its temporary is unlinked; a too-long name fails at `open`.
- 143 (make): reads the CompiledCode graph in a stop with bounds on blocks, elements and depth, refuses sealed literals, copies bytecodes, runs `verifyHeapMethod` on the method and every block, pins and marks read-only before answering (sound in itself; F1 is the un-protect path afterwards).
- 97/98: refused in a release image and for sealed classes except send-only extensions; the method must name the receiver and the selector and pass the verifier; install in a stop with cache flush.
- `instVarAt:`, `instVarAt:put:`, `slotAt:`, `shallowCopy`: index checked `1...count` before use, sealed and byte receivers refused where they write, keep-alive barrier on every weak read path in these files.
- String primitives 120 to 136: each integer checked by itself before arithmetic (62-bit SmallIntegers cannot overflow `&- 1`), boundary checks before copies, `count(of:)` is the true length for long bytes so the 123 concatenation and 120 comparison are right, long bytes go through the polled paths, 128 refuses read-only and checks room.
- Primitive 38 over bytes: Strings and Symbols refused as receivers, read-only refused, bounds checked one by one, overlapping ascending copy refused.
- 167 to 170: limit checked `0...maxLargeCount` before use, class Array bounded by the class count, walks after the promote-all hook in a stop, Array allocated old in the stop with the stop's roots, refilled when the allocation collected.
- 150/164 decode: op a String or Symbol, handle nil or SmallInteger, Array of immediates, Floats and short texts only; blocking region around the host call; 152 release with any SmallInteger is a no-op for an unknown handle in both hosts (`entries.removeValue`).
- 159 to 161 refused in a release image; 161 accepts only one line of valid UTF-8 between braces with no CR or LF.
- Token: compared in constant time over the expected length; never printed by the server, the reflection mirrors hide it, the TXT record carries image, protocol and kernel only; the token store file is created `O_EXCL | O_NOFOLLOW` at 0600 and renamed into place; typed tokens stay in `ClientHost` and the image sees only a 0/1 flag.
- Three wrong `session.open` close a connection, a first request that is not `session.open` closes it, both count towards the ten-in-a-minute pause; `session.open`/`session.close` from a client after the open are refused; a request over 16 MiB - 1 is refused with a reply.

- Unix socket: path length checked, an existing non-socket refused, a live socket refused, mode 0600 set before `listen`.
