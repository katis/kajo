## Findings (ranked, most severe first)

### F1. `zeroLongBytes` polls without rechecking its object, and primitive 167 makes that object reachable: a two-way become in a poll's stop turns the zeroing into a memset past another object's body
- Severity: critical   Confidence: confirmed (traced by reading, not run)
- Where: `Sources/KajoVM/ObjectModel/LongBytes.swift:86-107` (`zeroLongBytes`) and `:168-172` (`zeroBytes`, guarded only by `assert`); `Sources/KajoVM/Interpreter/InterpreterState.swift:252-254` (allocateLarge: `deferZero`, then `zeroLongBytes`); `Sources/KajoVM/ObjectMemory/LargeObjects.swift:73-80` (the old-map bit is set before the bytes are zeroed); `Sources/KajoVM/ObjectMemory/Instances.swift:22-45` and `ObjectModel/InstancePrimitives.swift:198-223` (primitive 167 returns every entry whose old-map bit is set).
- Invariant: the comment at the top of `LongBytes.swift` (lines 16-20) says: "After a poll that parked, the primitive checks its objects' lengths again (a two-way become in that stop may have swapped a body under it) and fails if any changed." `zeroLongBytes` was exempt because its object was fresh, and so nothing else could name it. Since the discoverability follow-up (primitive 167, `allInstances`), every entry with an old-map bit can be named by any Process. A large object gets its bit in `tryAllocateLarge`, before `zeroLongBytes` runs.
- Path that breaks it: VM with at least 2 workers. On worker A, Process P1 runs `ByteArray new: 1 << 30` (≥ `Header.longBytesFrom`, so `deferZero`). `zeroLongBytes` computes `total` once, then memsets 256 KiB chunks. Between chunks it calls `byteWorkPoll`, which parks for any requested stop. On worker B, Process P2 runs `ByteArray allInstances` (167). Its `instances` stop finds the new object: header class ByteArray, old-map bit set. P2 then sends `big become: (ByteArray new: 8)`. `Machine.become` refuses only sealed and read-only objects, so `becomeExchange` swaps the two state words in a second stop, with A parked again. When A resumes, `om.zeroBytes(o, from: i, to: end)` takes the body offset from `o`'s entry, which is now the 8-byte object's body. It writes `end - i` (up to 256 KiB) zeros at that body + 8 + i, where `i` can be hundreds of MB. The write lands across unrelated bodies and back references, or outside the heap reservation. The `assert` in `zeroBytes` is compiled out in release. Even without become, P2 can read the not-yet-zeroed tail: stale bytes of freed objects, a wrong answer. Writes P2 makes into the tail are then wiped by the zeroing. The window is 64 polls for a 16 MiB object and about 4096 polls (40 to 100 ms) for a gigabyte.
- Neighbours that have it right: `copyBytesPolled` (`LongBytes.swift:130`), `overChunks` (`:156`), `isValidUTF8Long` (`:294`) and `indexOfLong` (`:314`) all re-read `count(of:)` after a poll that parked, and fail when a count changed.
- Test that would fail today: in the large-bytes suite, run two workers. P1 allocates a long ByteArray (just over 16 MiB is enough). P2 waits until the allocation has begun (a test hook in `zeroLongBytes`, or `byteWork.polls > 0`), then calls `ByteArray allInstances` and `become:`s the long one with an 8-byte ByteArray. Assert that the heap verifier passes and that the 8-byte object's neighbours keep their checksums. A second, read-only variant asserts that a long ByteArray returned by 167 is all zeros.
- Fix sketch: after each poll that parked, check that `o`'s length and body offset are unchanged, and stop zeroing if not, as the other polled loops do. That alone still exposes junk bytes, so also keep the object out of the instance walks until it is initialised: either set its old-map bit only after `zeroLongBytes` finishes (it is a pending root meanwhile, so it stays alive), or skip pending-root objects in `walkInstances`. The same point covers F4.

### F2. Primitive 38 over pointer objects and `shallowCopy` of a large pointer object never poll (up to 16 777 215 slots with barriers in one go)
- Severity: medium   Confidence: likely (cost estimated, not measured)
- Where: `Sources/KajoVM/Relocation/Hazard.swift:82-183` (`primReplace` / `copySlots`: "the loop never polls"); `Sources/KajoVM/ObjectModel/ObjectModelPrimitives.swift:193-204` (pointer `shallowCopy`).
- Invariant: large-bytes.md and the head of `LongBytes.swift`: "no primitive over bytes keeps a stop waiting longer than one chunk of work". Module 10 says the marker polls inside a large object for the same reason. The pointer copies over the same large objects were never chunked.
- Path that breaks it: `(Array new: 16000000) replaceFrom: 1 to: 16000000 with: other startingAt: 1`, or `bigArray copy`, on a background worker. That is 16 M iterations with the barrier word checked, a seq_cst store and an insertion-barrier test per slot, plus an SATB push while a cycle marks. Tens of ms with no poll, so every stop waits that long and the main thread misses frames. The hazard slots are held for the whole loop.
- Neighbours that have it right: `primReplaceBytes` and `fillFresh` (polled per 256 KiB), and the marker's `traceChunk`.
- Test that would fail today: extend the large-bytes "longest stretch between polls" test to `replaceFrom:to:with:startingAt:` and `shallowCopy` on a 4 M-slot Array. A request for a stop from another worker should be answered within one chunk's time.
- Fix sketch: split `copySlots` into chunks of about 32 K slots. Release both hazard slots, call a poll that parks, re-acquire, and recheck both counts, as `copyBytesPolled` does. In `shallowCopy`, register the copy as a pending root and poll between chunks.

### F3. The final mark's weak-slot pass is unbounded per large weak object
- Severity: low   Confidence: likely
- Where: `Sources/KajoVM/Marking/FinalMark.swift:155-173`.
- Invariant: final-mark.md bounds the stop's tracing. It lists the weak pass as "measured, not bounded" and "proportional to the weak holders the marker met", but the cost is proportional to their indexed slots. Since module 10 a WeakArray can have up to 16 777 215 of them.
- Path: a program keeps a large weak cache, e.g. `WeakArray new: 10000000`. Every final mark loops over all 10 M slots in the stop, with a snapshot-bitmap and mark-byte load each. That is roughly 10 to 40 ms per final mark, on the main thread's frame budget too.
- Neighbours: the tracing before the commit point is bounded (`finalMarkWork`), and the marker chunks large objects.
- Test: a final-mark record test with a 4 M-slot WeakArray, asserting `weakNs` stays under the stop bound.
- Fix sketch: nil weak slots concurrently on the marker, after the commit point and before the sweep can free their referents. A snapshot entry stays unfreed until the sweep passes it, so the pass can run outside the stop if the sweep waits for it. Failing that, measure it and record it as a documented limit.

### F4. Objects still being built by a polled primitive are visible to primitive 167
- Severity: low   Confidence: confirmed (by reading)
- Where: `LongBytes.swift:204-218` (`fillFresh`, the destination a pending root while it polls), with callers in `Strings.swift:258-261, 289-291, 316-318` (123, 127, 130/131) and `ObjectModelPrimitives.swift:187-190`.
- Invariant: `Strings.swift` header: "a String stays valid from its creation (validated or built from valid pieces) on". `fillFresh`'s comment: the destination is "held by nothing but this primitive".
- Path: one Process concatenates two Strings of more than 256 KiB (123) on one worker. Another Process on another worker runs `String allInstances` during one of the copy's polls. It receives the new String with a prefix copied up to a 256 KiB boundary and zeros after it. If that boundary falls inside a multibyte scalar, the String is invalid UTF-8. A `become:` with a same-length long object passes `copyBytesPolled`'s count check, and the copy then finishes into the other object.
- Fix sketch: the same as F1's second half (no old-map bit, or skip pending roots in the walk, while a primitive builds the object).

## Checked and sound
- The keep-alive read barrier against today's slot readers: `at:` (Primitives.swift:80-83); `instVarAt:` (ObjectModelPrimitives.swift:169-171); `slotAt:` (KernelPrimitives.swift:50-52); `shallowCopy` of a weak receiver; `copySlots`' pre-pass `copyKeepAlive`; the symbol lookups (`intern`, 135) and bucket growth (Strings.swift:124, 172, 352). The new inline `at:` fast paths (Dispatch.swift:185-197, Special.swift:49-71, 416-425) and `spreadArray` admit only class index Array or ByteArray, never a weak class. The shell's `decodeViewCall`/`lineBytes` and `appendJSON` take Array only.
- Primitives 167 to 170 run inside a stop after the promote-all hook, which aborts marking, finishes the sweep unbounded and applies it. So the walks need no barrier, pin or hazard, and the answer's stores need none. The answer Array is allocated in the stop with `stop.roots()`. A collection during that allocation is detected through `counters.collections`, which compaction increments too. In that case the walk is repeated skipping the answer, and a smaller second Array is made rooted by the first. Limits are checked before allocating, and `instanceClassFlags` bounds class indices by `classCount`.
- The old map holds exactly the used old entries at the hook's end. Bits are set in `place`, `tryAllocateLarge` and promotion (Scavenge.swift:613/674, Collect.swift:668/720). They are cleared by the lazy sweep, `applyAheadOfCursor` (test only), `becomeForward` and module 1's `sweepEntries` rebuild, and rebuilt on load (Snapshot.swift:347). No other path frees an old entry.
- The partial apply `publishSwept` hands over only runs below the cursor whose snapshot words are cleared. A bounded sweep cuts the relocation pass off first. Blocks, pending-dead and the marking flag wait for the whole apply.
- `waitForMarkingCycle` and `waitForSweep` are bounded, never run on worker 0, root their object as a pending root, and park and service rounds every 100 µs.
- Pending roots are scanned both by `gatherRoots` and by module 7's `globalRoots` (Collect.swift:601-611).
- `stopWorld`: the request broadcasts to waits inside the VM; a released worker is not counted for the next stop (parked zeroed by the stopper); `relocationAtPauseStart`/`End` bracket every stop's work; `gatherRoots` covers ready queues, record stacks through the right sp, running workers' receiver, method and result registers, and pending roots.
- The young-root scan reads every slot of a young body, weak and ephemeron slots included. A collector or a module 4 scavenge finishes an owed scan before anything of its nursery moves. The SATB barrier records stores into young holders while their scan is owed, both in `satbRecord` and in `copySlots`' inline copy of it.
- The final mark runs the remembered filter after the ephemerons and nils weak slots only of holders the marker traced. Every give-up happens before the commit point.
- Byte primitives 120 to 134 over long objects check counts after every poll that parked. `compareBytes`/`moveBytes` use raw `memcmp`/`memmove` only when both objects are large (runs never move). `primReplaceBytes` checks its bounds one by one before any arithmetic; the short path stores through `checkedStoreByte`.
- `becomeExchange` keeps each body's word count (long bytes' length is in the back reference) and runs the hook before swapping. `becomeForward` refuses chains and frees sources with their old-map bits. `prepareReshape` runs the hook before listing instances and takes runs against the hard limit.
- `byteWorkPoll` advances the epoch before parking. `zeroBytes`/`moveBytes` take the body offset from the entry at every chunk; the defect in F1 is the missing length check, not a cached pointer.
